01

The Game

Ten Points A Word

It is a journal that runs in a terminal. You open it, you type, and a number in the header goes up. Every finished word is worth ten points, multiplied by a combo meter that climbs while you keep going and drains when you stop. The session ends with a score, and the score goes into a lifetime total that only ever grows. Text lives in a SQLite file at ~/.journal/journal.db.

The combo is the whole idea. A word typed in a steady run is worth up to five times a word typed after a long stare at the ceiling. That is a strange thing to do to a journal, and it is the point: the app is trying to buy you a few more minutes of writing before you stop.

The Constants

The rules of the game are eight numbers in one file. They are worth reading before the rest of the article, because everything that follows is a consequence of them.

the whole rulebook internal/scoring/combo.go
const (
	ComboFloor = 1.0
	ComboCap   = 5.0

	ComboBumpPerWords = 3
	ComboBumpAmount   = 0.1
	ComboBumpMaxGap   = 1500 * time.Millisecond

	ComboDecayStartGap      = 2 * time.Second
	ComboDecayRatePerSecond = 0.08

	ComboHardResetGap = 15 * time.Second

	BasePointsPerWord = 10
)
Three words in a row, each within 1.5 seconds of the last, buy 0.1 on the multiplier. Stop for two seconds and it starts draining at 0.08 a second. Stop for fifteen and it is back to 1.0 whatever it was before.

The multiplier is not a score of the session. It is a reading of the last few seconds. Getting to 5.0 takes about two minutes of unbroken typing, and losing it takes fifteen seconds of not typing. A streak bonus sits on top at the end — 5% per consecutive day, capped at 50% — and that one is about the long run.

02

The Reading

The Spike

A game that rewards pace needs to know your pace, and the header wants to show it live. The obvious way to measure it is wrong in a way that only shows up in the first few seconds.

why the denominator has a floor internal/scoring/intensity.go
	// PaceMinElapsed floors the denominator in WPM so the first couple of
	// words in a session (or right after a long pause) don't produce a
	// spurious spike — e.g. 2 words 1 real second apart would otherwise
	// imply 120 WPM.
	PaceMinElapsed = 5 * time.Second
Two words, one second apart, is a true measurement and a useless one. Without the floor the header opens every session by telling you that you write at 120 words a minute.

Pace is counted over a sliding sixty second window, kept separately from the combo. The combo is game feel; this is meant to be a fact.

Median, Not Average

The app also keeps a personal baseline, so it can say whether today is faster than usual. The number it compares against cannot be total words divided by session length, and the reason is written into the type that fixes it.

the baseline problem internal/scoring/intensity.go
// PaceSampler collects live WPM readings taken while the writer is actively
// typing. Its median is the session's representative pace, and unlike a
// wall-clock average (total words ÷ session duration) it isn't dragged
// toward zero by thinking time — which matters because the same readings
// are what the intensity ratio divides by. Comparing a burst-measured live
// reading against a pause-diluted baseline inflates every ratio.
A journal session is mostly pauses. Divide by the wall clock and the baseline sinks, and then every live reading looks like a personal best.

An empty string doing real work. The retrospective tag and the live header use two different functions on purpose. IntensityTier returns nothing at ordinary pace, so old sessions written before a baseline existed stay unlabelled instead of carrying a word they never earned. LiveTier always returns a word — Warming, Cruising, Focused, Intense, Frantic — because a header that goes blank is a header you stop trusting.

03

The Crash

One Row Per Session

A journal you might lose is not a journal. The editor writes what is on screen to disk every five seconds, into a table that holds one row per session and replaces it each time.

the draft table internal/store/store.go
CREATE TABLE IF NOT EXISTS drafts (
	session_id INTEGER PRIMARY KEY REFERENCES sessions(id),
	body TEXT NOT NULL,
	body_words INTEGER NOT NULL,
	raw_score INTEGER NOT NULL,
	total_words INTEGER NOT NULL,
	updated_at TEXT NOT NULL
);
It mirrors the buffer rather than recording a history, so it stays the size of what you have written no matter how many hours the session runs. The score is stored beside the text because a combo history cannot be rebuilt after the fact.

The help line at the bottom of the writing screen says saved or unsaved. That is there because the whole value of autosaving is not having to wonder, and a silent autosave gives you no way to tell the difference between working and broken.

Back At 1.0

Resuming puts the text back in the editor and the running score back on the header. It does not put the combo back, and the reason is the most honest line in the codebase.

what a resumed session gets back internal/scoring/session.go
// The combo deliberately restarts at the floor. It measures the rhythm of
// the last few seconds of typing, and the interruption ended that rhythm —
// restoring a 4x multiplier would hand out points for momentum that no
// longer exists.
Giving the multiplier back would be the friendly choice and the wrong one. The number claims to describe the last few seconds, and the last few seconds were a crash.

Sessions that were opened and never written in are deleted quietly. Offering someone an empty session back is not crash recovery, it is a chore.

The Word "up"

Typed, Not Pressed

Typing the word "up" did not put "up" on the page. It moved the cursor up a line and the two letters vanished. Typing "esc" in the middle of a sentence ended the session.

captured from a real run commit 30350b3
...and ask about the repor exactly where the battery cut me off. ting
deadline before committing to anything else this week.
The cursor jumped mid-word, so the rest of the sentence landed inside an earlier paragraph. The text is not dropped, it is rearranged — which is worse, because it survives to be read back later.
why it happened internal/tui/writing.go
		// bubbletea coalesces the runes it reads in one go into a single
		// KeyMsg, and Key.String() renders that run as a plain string — so a
		// message carrying the typed letters "up" is indistinguishable from
		// the up-arrow key, and one carrying "esc" from escape. Both bubbles'
		// key bindings and the switch below match on that string, so typing
		// "up" moved the cursor instead of writing the word, and typing "esc"
		// mid-sentence ended the session. A run of more than one rune is
		// always text a person typed, never a key they pressed: insert it
		// directly and let no binding look at it.
		if keyMsg.Type == tea.KeyRunes && len(keyMsg.Runes) > 1 {
			m.writing.textarea.InsertString(string(keyMsg.Runes))
The fix is the rule in the comment: more than one rune at once is always text somebody typed. Insert it directly so no key binding ever looks at it, and match this screen's own keys on the message type rather than its string.

This was not a fast-typing edge case. It reproduced at a deliberate 120 milliseconds per word against the real binary. The words that broke it are ordinary ones — up, down, left, right, home, end, tab, space, delete, esc — and a journal is made of ordinary words.

Words Nobody Typed

A score for typing is only worth something if it cannot be bought. Two guards do that job, and the second one exists because the first one is not enough on its own.

paste is blocked

A terminal paste arrives flagged as a paste no matter how many characters it carries, and the writing screen refuses it with a warning line. The line has space reserved even when it is not showing, so a paste attempt never pushes the editor off the bottom of the screen.

twenty words per update

A single update can score at most twenty words. If a paste ever gets past the first guard, it cannot award thousands of points and stamp thousands of words at one instant — which would spike the pace reading to an impossible value and poison the personal baseline built from it.

The clamp protects the measurement, not the score. Losing points to a bug is annoying. A poisoned baseline quietly changes every intensity reading afterwards, and nothing on screen would say so.
