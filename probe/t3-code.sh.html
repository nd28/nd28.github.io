01

The Friction

What It Cost To Open An App

The file was T3-Code-0.0.33-x86_64.AppImage, in ~/Downloads, executable, working. An AppImage is a single file. Nothing installs it, so nothing tells the desktop it exists. It does not appear in the app list and it has no icon anywhere. The only way in was the file manager.

opening the app
before 4 steps, about 15 seconds open Downloads → type "t3" in search → right click → Run → wait ~3s for the window
after 1 key, or nothing at all Super+T from anywhere, and it is already open after login

The cost is not the seconds. The person asking has ADHD. Four steps is four chances to get pulled somewhere else, and a file manager is full of other things to look at. So the fix is not "make it faster" — it is to remove the places where attention can leak out.

Reading The Machine First

Two things decided the whole approach, so they were checked before anything was written.

Ubuntu GNOME on Wayland

GNOME reads autostart entries from ~/.config/autostart and app entries from ~/.local/share/applications. Both are plain .desktop files. No package manager involved.

libfuse2 present

/usr/lib/x86_64-linux-gnu/libfuse.so.2 was there. AppImages mount themselves with FUSE. Without it the file needs an extract-and-run workaround, and every path below would have changed.

Wayland removed an option. On X11 a script can raise another window. On Wayland it cannot, so the shortcut had to work without ever asking the compositor to focus anything.

02

The Install

One Symlink, Everything Else Points At It

The AppImage moved out of ~/Downloads — that folder gets emptied, and a 153 MB file with a version in its name is easy to delete by accident. It went to ~/Applications. Then the one decision that made the rest simple: nothing refers to the versioned filename. Everything refers to a symlink.

~/Applications/T3-Code-0.0.33-x86_64.AppImagebinarythe real file, version in the name
~/.local/bin/t3-codesymlinkthe stable name — on PATH, so it is also a terminal command
~/.local/share/applications/t3code.desktopdesktopapp list entry — Super, type "t3", Enter
~/.config/autostart/t3code.desktopdesktoplogin autostart, 8 second delay
~/.local/share/icons/hicolor/512x512/apps/t3code.pngpngicon, found by theme lookup
~/.local/bin/t3-code-updaterbashfetch, verify, swap the symlink, prune

A version bump now touches one thing. Point the symlink at the new file and the app list, the autostart entry, the shortcut and the terminal command all follow. Without the symlink, every update means editing three files and remembering that the third one exists.

the autostart entry ~/.config/autostart/t3code.desktop
[Desktop Entry]
Type=Application
Name=T3 Code (Alpha)
Comment=Start T3 Code automatically on login
Exec=/home/<user>/.local/bin/t3-code --no-sandbox   // the symlink, never the versioned file
Icon=t3code
Terminal=false
StartupWMClass=t3code
X-GNOME-Autostart-enabled=true
X-GNOME-Autostart-Delay=8
The 8 second delay is deliberate. Starting a 153 MB Electron app at the same moment as the shell makes login feel slow, and login is exactly when a slow desktop is most annoying.

Both files were checked with desktop-file-validate before anything was launched. A .desktop file with one bad line does not error. It just silently never appears, and then you are debugging the wrong thing.

The Icon Was A Broken Link

AppImages carry a desktop entry and an icon inside them. Pulling them out is one command:

extracting the icon two tries
$ t3-code --appimage-extract '*.png'
  squashfs-root/t3code.png

$ file squashfs-root/t3code.png
  broken symbolic link to usr/share/icons/hicolor/512x512/apps/t3code.png

$ t3-code --appimage-extract 'usr/share/icons/hicolor/512x512/apps/t3code.png'
  PNG image data, 512 x 512, 8-bit/color RGBA
The top-level t3code.png is a symlink into a directory the pattern did not match, so the first extract produced a link pointing at nothing. Copying it would have installed a broken file and the app would have shown a generic grey icon with no error anywhere.

The real icon went to the hicolor theme path, so the desktop entry can say Icon=t3code and let the icon theme resolve it, instead of hardcoding a path that a future update might invalidate.

03

The Ordering Trap

The app was launched through its new desktop entry to confirm it worked. It did — the log said main window created. But a check of the files afterwards showed something that had not been there a minute earlier.

The app writes its own desktop files. On launch, T3 Code registered itself as the handler for the t3code:// URL scheme. It rewrote t3code.desktop and created a second file, t3code-url-handler.desktop, that nobody asked for.

written by the app, not by us ~/.local/share/applications/t3code-url-handler.desktop
[Desktop Entry]
Type=Application
Name=T3 Code (Alpha)
Exec="/home/<user>/Applications/T3-Code-0.0.33-x86_64.AppImage" %U
Terminal=false
NoDisplay=true
MimeType=x-scheme-handler/t3code;
Note the Exec line: an absolute path to the versioned file, not the symlink. The app bakes in wherever it was started from.

This is the part worth remembering. The file had been moved to ~/Applications before the first launch, so the path the app recorded is permanent. Had it been launched once from ~/Downloads first — the obvious way to test "does this thing even run" — that Exec line would point at a file that no longer exists, and every t3code:// link would silently fail later, long after anyone would connect it to a file move.

Move first, launch second. With self-registering apps the first launch is not a neutral test. It is a write. The order of two commands decided whether a feature works in three months.

You cannot stop it, only get there first. The entry is rewritten on every launch, so fighting it is pointless. Giving it the right path once is enough.

04

One Keystroke

Launch Or Raise, Same Command

A shortcut that only launches is half a shortcut. If the app is already open, pressing the key should bring it forward, not start a second copy. On Wayland a script cannot raise someone else's window, so this had to be solved by the app or not at all.

The app's own log had a hint that pointed the wrong way — it picks its backend port by scanning upward from 3773, which is what you would build if you expected several copies to run at once. Rather than guess, the behaviour was measured: record the main process ID, run the launch command again, compare.

second-instance test measured, not assumed
main pids before: 395964
$ t3-code --no-sandbox        // launched again while running
main pids after:  395964

→ no new process. single-instance lock. the existing window took focus.
The port scan was a red herring. One launch command does both jobs, so the shortcut stays a single line with no window management in it.

Picking A Key That Was Free

GNOME keeps shortcuts in three separate schemas, and a clash does not warn you — the older binding just wins and your new one does nothing. All three were checked before choosing.

conflict check gsettings
org.gnome.desktop.wm.keybindings              → Super+T free
org.gnome.shell.keybindings                   → Super+T free
org.gnome.settings-daemon.plugins.media-keys  → Super+T free
custom-keybindings                            → @as [] (none defined)
Super+T is free on stock Ubuntu GNOME. Ctrl+Alt+T, the reflex choice, is the terminal.

The binding was written as a custom keybinding under a named path — .../custom-keybindings/t3code/ rather than the usual custom0. Named paths do not renumber when another shortcut is added later, and it shows up in Settings → Keyboard as a normal editable entry rather than something mysterious.

One honest gap. On Wayland a script cannot synthesise a real key press, so "Super+T works" was not directly proven. What was proven: the binding is stored correctly in dconf, and its exact command was run in both states — cold start produced a new window, and re-running while open produced no second process. The keypress itself is the one link in the chain a person still has to test.

05

The Updater

Do Not Guess The Repo

An updater needs to know where new versions come from. Searching for the project would have produced a plausible answer. The AppImage already contained the exact answer, because Electron apps ship their updater config inside the bundle.

the app's own updater config resources/app-update.yml
owner: pingdotgg
repo: t3code
provider: github
releaseType: release
Extracted from the AppImage, not searched for. The script now reads from the same source the app itself would use.

The releases carry a manifest, latest-linux.yml, published by the build tool. It gives three things the updater needs and would otherwise have to infer: the version, the exact asset filename, and a SHA-512 of the file in base64.

verification, proven before it was trusted openssl + base64
expected  (from latest-linux.yml)  l0PazCB8U3UDCVHEaINaLzGG…
actual    (installed file on disk)  l0PazCB8U3UDCVHEaINaLzGG…
MATCH
Run against the already-installed file first. A checksum check that has never produced a match is not a check, it is a hope.

Three Things It Refuses To Do

Most of the script is not downloading. Downloading is four lines. The rest is the list of ways an update can quietly damage a working setup.

will not install a file it cannot verify

SHA-512 is compared before the file is moved anywhere. On mismatch it stops and prints both values. It also runs --appimage-offset as a cheap sanity check, which catches the case where an HTML error page was saved with a 200 status.

will not downgrade

If the installed version is newer than the latest release — which happens when a release is pulled — it says so and stops instead of "updating" you backwards. --force is there for when that is actually what you want.

will not delete a running version

Pruning old AppImages reads APPIMAGE out of /proc/<pid>/environ for every live process and skips any file still in use. Deleting the image a running app is mounted from is how you get an app that works until you close it.

The swap is a rename, not a delete. There is no moment where t3-code points at nothing. If the machine dies in the middle of an update, the old version is still what runs.

a real run t3-code-updater --force --keep 2
==> checking https://github.com/pingdotgg/t3code/releases/latest
  installed: 0.0.33
  latest:    0.0.33
==> downloading T3-Code-0.0.33-x86_64.AppImage
==> verifying sha512
  checksum ok
==> symlink -> T3-Code-0.0.33-x86_64.AppImage
  pruned T3-Code-0.0.31-x86_64.AppImage

reinstalled T3 Code 0.0.33
T3 Code is running -- quit and reopen it to use the new version.

real  0m11.016s
153 MB fetched, hashed, installed and pruned in 11 seconds. Two fake old versions were placed on disk first so the prune path actually ran instead of being assumed to work.

One pleasant surprise: the running app survived having its own file replaced underneath it. The FUSE mount holds the old inode open, so a rename only changes the name, not what the running process is reading. It keeps working until you close it, which is exactly the honest thing for the script to say.

06

The Bugs

Three real ones, all found by running things rather than reading them.

The new file came out with the wrong permissions. mktemp creates files as 0600. Adding chmod +x to that gives 0711, not the 0755 everything else on the system has. It ran fine for the owner, so nothing failed — it was only visible in an ls -l after the first real update. Fixed by setting the mode explicitly instead of adding to whatever was already there.

Redirection order leaked errors. The prune step reads /proc/<pid>/environ, and short-lived processes disappear between listing them and reading them. The line was written as tr … < /proc/$pid/environ 2>/dev/null, which looks safe and is not: the shell applies redirections left to right, so the input redirect fails and prints its error while stderr is still the terminal. The suppression arrives one step too late. Fixed by testing the file is readable first.

A cleanup command killed the session running it. pkill -f 't3code' matches against full command lines — including the command line of the shell that is running pkill, because the pattern appears in it. It killed the app, then killed itself, and the whole step exited with code 144 halfway through. The fix is the old bracket trick: write the pattern as [t]3code, which still matches the target but no longer matches the literal text sitting in the shell's own command line.

What The Session Actually Looked Like

Very little of this was writing. Most of it was checking that assumptions were true before building on them, and most of the checks were cheap.

checked, not assumed

FUSE present. Super+T free in all three schemas. Single-instance lock real. Checksum logic matched a known-good file. Prune path exercised with throwaway files.

found by accident

The self-registering desktop entry only surfaced because a file listing after launch showed a timestamp one minute newer than expected. Nothing pointed at it.

still open

The physical key press. And the app has its own built-in updater, so if it ever replaces itself under a different filename the symlink will dangle — t3-code-updater --force puts it back.
